# سير عمل المراجعة — Review Workflow

## الأدوات المستخدمة

يستخدم المشروع GitHub Issues كنموذج إدخال ومتابعة، وPull Requests كسجل للتغييرات المقترحة، وGitHub Actions للفحوص الآلية. لا توجد حالياً لوحة تحكم خارجية أو حسابات مراجعين منفصلة؛ صلاحيات المراجعة تتبع صلاحيات مستودع GitHub.

## حالات العمل

```text
Issue opened
   |
   v
pending -> in_review
   |          |
   |          +--> needs_correction -> contributor update -> in_review
   |          |
   |          +--> rejected (reason recorded)
   |
   +--> reviewed (human evidence recorded)
                 |
                 v
           Pull Request
                 |
          automated checks
                 |
           maintainer review
                 |
             merge / close
```

## قائمة تحقق المراجع

### لغوي
- هل التعبير دارج فعلاً؟
- هل الرسم العربي يحافظ على الاستعمال؟
- هل الكتابة اللاتينية تمثيل ممكن ومفهوم؟
- هل المقابل بالفصحى والفرنسية دقيق في السياق؟
- هل المثال يوضح المعنى دون كشف بيانات خاصة؟

### اجتماعي/جهوي
- هل الادعاء الجهوي مدعوم؟
- هل يختلف المعنى أو النطق حسب السياق أو المنطقة؟
- هل تم تجنب تقديم متغير محلي باعتباره الصيغة الوحيدة؟

### مصدر وحقوق
- هل المصدر قابل للتحقق؟
- هل صاحب الحقوق معروف؟
- هل أذونات إعادة التوزيع والتدريب والتجارة موثقة كل على حدة؟
- إذا بقيت الحقوق مجهولة، هل ظلت القيمة unknown؟

### القرار
وثّق القرار مع السبب والدليل:
- قبول: بعد المراجعة البشرية.
- طلب تعديل: حدد الحقل والمعلومة الناقصة.
- رفض: وضح التكرار أو الخطأ أو مشكلة المصدر/الحقوق.

لا تعتمد `reviewed` بناءً على نجاح CI وحده. لا تدمج أي مدخل يفتقر إلى أساس لغوي أو حقوقي كافٍ لمجرد استكمال الحقول.

## سياسة حفظ سجل المراجعة

ضع حالة المراجعة ومعرف المراجع وتاريخها وملاحظة مختصرة في سجل البيانات أو في PR المرتبط. استخدم معرفاً مستعاراً عند الحاجة. لا تسجل أسماء حقيقية أو معلومات اتصال إلا إذا كان ذلك ضرورياً وموافقاً عليه.
